## 2. 장바구니를 서버로 옮기기 (SCRUM-28)

인수 당시 장바구니는 브라우저 `sessionStorage`에만 있었다. 탭을 닫으면 사라지고, 다른 기기에서는 보이지 않는다.

- `CartProvider`가 `/cart` API를 호출하도록 바꿨다.
- 로그인하지 않았으면 담기 대신 로그인 화면으로 보낸다. 비회원 장바구니는 만들지 않았다.
- 로그인한 회원이 바뀌면 `GET /cart`로 다시 불러온다.
- 상태는 일부만 고치지 않고, 서버 응답 전체로 교체한다.

```
GET    /cart                     장바구니 조회
POST   /cart/items               담기 (수량 합산)
PATCH  /cart/items/{productId}   수량 변경
DELETE /cart/items/{productId}   한 줄 삭제
DELETE /cart                     비우기
```

후속 PR(#29)에서 두 가지를 고쳤다.

| 문제 | 해결 |
|---|---|
| 재고가 줄어든 상품이 담겨 있으면 409(재고 초과)가 반복됨 | 재고 감소 시 409가 반복되지 않도록 수정 |
| 품절 상품이 있어도 주문하기로 넘어갈 수 있음 | 품절 상품이 있으면 주문 버튼 잠금 |

## 3. 주문 생성은 한 트랜잭션으로 (SCRUM-29)

주문 한 번에 여러 테이블이 바뀐다. 중간에 하나만 실패해도 재고와 주문이 어긋나므로 전부 한 트랜잭션으로 묶었다.

```
1. 장바구니 행 잠금        cart_item  FOR UPDATE
2. 상품 행 잠금            product    FOR UPDATE  (product_id 순서대로)
3. 재고 차감               Product.decrease_stock  (부족하면 409)
4. 주문 저장               orders · order_item · payment(결제완료) · 상태 이력(→접수)
5. 장바구니 비우기          DELETE cart_item
6. COMMIT                  (예외가 나면 ROLLBACK)
```

**정리한 개념**

- **트랜잭션**: 여러 작업을 "전부 성공 아니면 전부 취소"로 묶는 단위다. commit은 application 계층 서비스에서만 한다.
- **`FOR UPDATE`(행 잠금)**: 내가 읽은 행을 다른 트랜잭션이 바꾸지 못하게 잠근다. 동시에 같은 상품을 주문해도 재고가 음수가 되지 않는다.
- **교착(deadlock)**: A는 1번 → 2번, B는 2번 → 1번 순서로 잠그면 서로를 기다리다 멈춘다. 모든 요청이 `product_id` 순서로 잠그면 이 상황이 생기지 않는다.
- **409 Conflict**: 요청 형식은 맞지만 현재 상태와 충돌할 때 쓴다. 재고 부족, 빈 장바구니가 여기에 해당한다.

## 4. 주문 화면 API 전환 (SCRUM-30)

- 주문하기(`CheckoutForm`): 배송지 검증 → `POST /orders`
- 주문 완료(`OrderComplete`): `GET /orders/{id}`로 결과 조회
- localStorage에 주문을 저장하던 `orderStorage.createOrder` 삭제
- 성공하면 장바구니를 다시 불러오고 주문 완료 화면으로 이동한다.
- 409 등 오류가 나면 버튼 위에 메시지를 띄우고 장바구니를 다시 불러온다.
