## 9. groupby + agg

## 10. 결측값 확인

결측값 개수는 `isna().sum()`을 사용한다.

특정 컬럼:

```python
df["age"].isna().sum()
```

전체 컬럼:

```python
df.isna().sum()
```

DataFrame 전체 결측값 개수:

```python
df.isna().sum().sum()
```

예:

```python
"missing_values": int(frame.isna().sum().sum())
```

`isna().count()`는 결측값 개수를 세는 방법이 아니다.

## 11. 중복값 확인

전체 행 중복:

```python
frame.duplicated().sum()
```

특정 Key 중복:

```python
frame["customer_id"].duplicated().sum()
```

두 코드는 의미가 다르다.

```text
df.duplicated().sum()
→ 전체 행이 완전히 같은 중복

df["id"].duplicated().sum()
→ 특정 Key 값의 중복
```

## 16. PK 검증

주요 PK는 다음과 같다.

```text
customers → customer_id
products → product_id
orders → order_id
order_items → order_item_id
```

Key 정보를 딕셔너리로 관리할 수 있다.

```python
key_map = {
    "customers": "customer_id",
    "products": "product_id",
    "orders": "order_id",
    "order_items": "order_item_id"
}
```

PK 결측 및 중복 검사:

```python
pk_checks = []

for dataset, key in key_map.items():

    frame = processed_data[dataset]

    missing_count = int(frame[key].isna().sum())
    duplicated_count = int(frame[key].duplicated().sum())

    pk_checks.append({
        "dataset": dataset,
        "key": key,
        "missing_count": missing_count,
        "duplicated_count": duplicated_count
    })
```

정상 PK:

```text
missing_count == 0
duplicated_count == 0
```

## 19. merge()

Pandas의 `merge()`는 SQL JOIN과 비슷한 역할을 한다.

```python
order_sales = order_items.merge(
    orders[
        [
            "order_id",
            "customer_id",
            "order_date",
            "order_status"
        ]
    ],
    on="order_id",
    how="left",
    validate="many_to_one"
)
```

## 20. LEFT JOIN

```python
how="left"
```

왼쪽 DataFrame의 모든 데이터를 유지한다.

예:

```text
왼쪽: 1, 2, 3
오른쪽: 2, 3, 4

LEFT JOIN 결과: 1, 2, 3
```

---

## 21. INNER JOIN

```python
how="inner"
```

양쪽 테이블에 모두 존재하는 데이터만 남긴다.

```python
merged = order_items.merge(
    orders,
    on="order_id",
    how="inner"
)
```

예:

```text
order_items: 1, 2, 3
orders: 2, 3, 4

INNER JOIN 결과: 2, 3
```

## 22. validate="many_to_one"

```python
validate="many_to_one"
```

관계를 검증하는 옵션이다.

```text

→ 동일한 order_id 여러 개 가능

orders
→ order_id는 하나만 존재
```

즉 `N : 1` 관계를 의미한다.

## 28. 주문 상세 행 수와 주문 수의 차이

## 36. Total Consistency

같은 completed 주문을 기준으로 만들어진 금액 집계는 총합이 같아야 한다.

```text
completed source total
=
category total
=
monthly total
=
customer total
```

예:

```python
completed_total = completed_order_sales["line_total"].sum()
category_total = category_sales["total_sales"].sum()
monthly_total = monthly_sales["total_sales"].sum()
customer_total = customer_sales["total_sales"].sum()
```

검증:

```python
print(completed_total == category_total)
print(completed_total == monthly_total)
print(completed_total == customer_total)
```

같은 의미의 숫자가 서로 다르면 분석 결과를 해석하기 전에 계산 과정을 다시 확인해야 한다.

## 43. GitHub Push Protection

다음 오류가 발생할 수 있다.

```text
GH013:
Repository rule violations found

Push cannot contain secrets
```

GitHub가 커밋에서 비밀정보를 발견한 것이다.

예:

```text
Google OAuth Client ID
Google OAuth Client Secret
Slack Incoming Webhook
Slack API Token
GCP API Key
```

실제 API Key나 Secret을 GitHub에 올리면 안 된다.

## 44. .env 파일 관리

실제 비밀정보는 `.env`에 저장하고 Git에 올리지 않는다.

예:

```env
GOOGLE_OAUTH_CLIENT_ID=실제값
GOOGLE_OAUTH_CLIENT_SECRET=실제값
```

`.env.production.example` 같은 예제 파일에는 실제 값을 넣지 않는다.

예:

```env
GOOGLE_OAUTH_CLIENT_ID=
GOOGLE_OAUTH_CLIENT_SECRET=

GCP_API_KEY=replace-with-api-key
```

`.gitignore`에는 보통 다음을 추가한다.

```text
.env
.env.local
.env.production
```

## 45. Secret이 이미 Commit에 들어간 경우

파일에서 키를 삭제하는 것만으로 해결되지 않을 수 있다.

이유는 과거 Commit 안에 Secret이 남아 있기 때문이다.

최근 Commit이라면:

```bash
git add .env.production.example
git commit --amend --no-edit
```

그 후 다시 Push한다.

```bash
git push origin prd/yg
```

실제 Secret이 외부에 노출되었다면 해당 API Key나 Token을 폐기하고 새로 발급하는 것이 안전하다.

products["category"].value_counts()
